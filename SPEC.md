# rainofchaos — Spec

A static website that finds profitable Path of Exile currency-exchange round trips that start and end in the same currency (Divine, Chaos or, in PoE2, Exalted Orbs).

---

## 1. Scope

- **Games:** Path of Exile 1 and Path of Exile 2, PC realm only. Each game has its own address and its own data, settings and saved state (`html/js/game.js`):

  | | Path of Exile 1 | Path of Exile 2 |
  |---|---|---|
  | Address | `rainofchaos.app/poe1` | `rainofchaos.app/poe2` |
  | Hubs (routes go through these) | Chaos, Divine | Exalted, Divine (Chaos trades as an item) |
  | Start with (toggle order; first is default) | Chaos, Divine | Exalted, Divine |
  | Default starting amounts | 1,000c, 25 div | 2,000 ex, 3 div (about 3 div each) |
  | Extra items valued at what they sell for in | Chaos | Exalted (the busiest hub) |
  | Routes per item | 3 | 3 |
  | Data | `/rates.json`, `/data/catalog.json`, `/data/gold.json` | `/poe2/rates.json`, `/data/poe2/catalog.json`, `/data/poe2/gold.json` |
  | Saved state | `rainofchaos:v1` | `rainofchaos:poe2:v1` |

  Every route ends in the currency it starts in, in both games. The page itself is one file, served at `/`, `/poe1` and `/poe2`; the game comes from the address. `/` goes to the **last game visited**: every visit to either game records it (`rainofchaos:game` in localStorage), and with nothing recorded it's PoE1. A small **PoE1 / PoE2** dropdown sits right after the "rainofchaos" brand (a quiet, pill-shaped select in the accent colour), followed by the League dropdown. Switching opens that game's **home page** (`#/home`, its own description), whatever page you were on. `/poe1/` with a trailing slash isn't served.
  - **Not yet confirmed in game:** that PoE2's exchange shows ratios like PoE1's (two decimals, rounded half up), which the lot maths (§2.2) assumes, The exchange window itself is confirmed (one PoE2 frame, 2152 x 1243): the same font and row spacing, but its own buttons and a higher hover box, so each game has its own window style (§4.7).
- **Prices come from the game.** Competitive and Instant Trading calculate only with prices read from the game by the player in the last 4 hours (Import Market Ratios, §4.7, watching the game's window). Estimated Trading prices a pair with no such scan at its latest hour's average from `rates.json` (an **estimate**, §3.2c), for players whose imports don't work. The only typed prices are steps on My Listings set to Manual (§3.2b, §4.6). `rates.json` also gives volumes, stock, which directions have no orders and fill times.
- **League:** selectable, from a dropdown right after the PoE1 / PoE2 dropdown, styled the same way (a quiet, pill-shaped select in the accent colour), with no "League" label (the league names speak for themselves; the dropdown is named "League" for tooltips and screen readers). The default is the current softcore challenge league.
- **Currencies: no fixed list.** Every currency that traded against Chaos or against Divine within the last `DAYS` days (currently 1) in the selected league is included. That's about 850 in Allflame. The job finds them in the API data (§6.2).
- **Names and icons:** from `html/data/catalog.json`, built by `tools/catalog.py`.
  - **Names:** RePoE's `base_items.json` maps API metadata ids to names. The few divination cards missing from it are matched from their ids against the trade site's card list.
  - **Icons:** GGG CDN URLs, linked directly (poe.ninja and the trade site do the same). The source is the trade site's static data (`/api/trade/data/static`). Failing that, it's the item's art file from RePoE (`visual_identity.dds_file`), which the CDN serves as `/image/<path>.png?scale=1`. This covers league-specific items like Message in a Bottle. Divination cards without either use the generic card icon.
  - **Placeholder:** a currency not in the catalog, or whose image fails to load, shows a small grey "?" circle, with its name on hover.
  - **New currencies:** a currency not yet in the catalog shows a name derived from its id (`ScarabUber1` → "Scarab Uber 1") and the placeholder icon. Re-run `python3 tools/catalog.py`, then redeploy the site. A rebuild adds and updates the currencies trading now and keeps the rest, so one that isn't trading this hour keeps its name.
  - **Path of Exile 2** has its own catalog, `html/data/poe2/catalog.json`, built by `python3 tools/catalog.py poe2` from `poe2/rates.json`, RePoE's PoE2 export (`repoe-fork.github.io/poe2/base_items.json`) and the PoE2 trade site's static data (`/api/trade2/data/static`). It has no divination cards. The CDN doesn't serve PoE2 art files by path, so items without a trade-site image get the placeholder icon (8 of 667 at first build).
- **Gold fees:** the game's data has each currency's (its CurrencyExchange table's GoldPurchaseFee), and poedb lists them, one page per game; there's no GGG API for them.
  - **The shared list** is `html/data/gold.json` (id → gold per unit received), deployed with the site. `python3 tools/gold.py [poe1|poe2]` fills it from poedb (`poedb.tw/us/Currency_Exchange`, PoE2 `poe2db.tw/us/Currency_Exchange`), matching names through the catalog: it adds only fees the list doesn't have, keeps every fee already there, and reports any poedb gives differently. Run it when new currencies show up, after `tools/catalog.py`.
  - **No edits on the site:** fees are shown, never typed in. A currency the list doesn't have shows a dash until `tools/gold.py` is run again.
  - **Path of Exile 2** has its own list, `html/data/poe2/gold.json`, filled the same way (`tools/gold.py poe2`).
  - **Unknown fees:** a step with an unknown fee shows "—". A route total that includes one shows "> N", where N is the sum of the known steps. It shows "—" if no step's fee is known.
- **Icon display:**
  - Chaos and Divine appear as icons only (the name shows on hover) in quantities, profits and route labels.
  - Route labels show the item as an icon only too.
  - Ratio lines and the steps tables are icon-only for every currency, because a heading already names the item.
  - Elsewhere, items keep their name next to the icon.
  - An icon that starts a cell or line has no gap on its left (so it lines up with the heading above); an icon after a ratio's number (`3,096[chaos] : 1[div]`) always keeps its small gap from the number, even when it's the first icon in its cell.
  - Amounts (quantities, profits, profit per minute, gold, volumes) put the icon first: `[chaos]3,096`, `[div]+16`, `[gold]2,400`. Ratios keep their numbers first.
- **Starting currency ("Chaos or Div mode"):** the Trade Recommendations page (§4.1) and every item page (§4.2) show **Starting Amount:** [box] [one icon per start option: Chaos | Divine in PoE1, Exalted | Divine in PoE2], with the box sized for up to 6 digits, at the top right of the page, above the tabs, as tall as a button (the label, box and icons stretched to a button's height). It isn't in the header, since other pages don't use it. The icons are a toggle that picks the currency every route **starts and ends** in (the "base"), and profit is in that currency (§3.4). The selected icon sits on the accent colour and the other is faded. The amount is a whole number in that currency. The first option is the default (Chaos in PoE1, Exalted in PoE2). Any hub can be a start option (`starts` in `js/game.js`); PoE2's Chaos is a hub routes go through but isn't offered as a start. A saved start that isn't offered falls back to the first option. Each currency keeps its own amount (defaults above). Market Ratios is the same whatever you start with.
- **No backend.** The site is static on S3, and all user state lives in the browser. The only server-side piece is an hourly job that writes JSON files (§6).

## 2. Ratios

### 2.1 What a ratio is

Each directed pair `A:B` stores the ratio **exactly as the in-game exchange displays it**: two numbers, usually one of them `1`, with at most 2 decimals. Examples: `380 : 1`, `1 : 8.27`.

For each item there are 4 directed pairs, and there are 2 for Chaos↔Divine:

```
Item:Chaos   Chaos:Item   Item:Divine   Divine:Item
Chaos:Divine Divine:Chaos
```

`A:B` is the rate at which you **receive A for B when you post your own order** (Slow). The same row read backwards is what a **Fast** trader pays/gets (see §3.2).

**How the UI maps to the game.** The exchange shows a pair the same way round both times, as `A : B`.
- **By default** it shows **Available Trades**: the orders already on the other side, which you can fill instantly. This is internal row `B:A`.
- **With Alt held** it shows **Competing Trades**: the competitive price you'd post at and wait for. This is internal row `A:B`.

Example: `Chaos 371 : 1 Divine` by default, and `Chaos 380 : 1 Divine` with Alt held (sell 1 div for up to 380c).

Each line in the site's ratio tables mirrors this, with two columns in the same `A : B` orientation:
- **Traded last hour** (right-hand column, so the two price columns sit together): how much of each currency traded in that pair's latest hour in `rates.json`, e.g. `[vivid]376,713 ⇄ [chaos]32,772`. A pair with no data shows 0 for each (`[vivid]0 ⇄ [chaos]0`), as does a hub market with none in an item page's volume (`0c + 89 div`, §4.2).
- **Available Trades:** shows row `B:A`, drawn flipped.
- **Competing Trades:** shows row `A:B`.

Both are read-only: they show what was read from the game (§4.7), with the decimals it showed, "no trades" where the game showed that box empty, or "not scanned". The calculation (§3) uses the internal rows unchanged.

### 2.1a Directions with no orders

The game can show "There are no available trades" or "There are no competing trades" for a pair. The API's per-hour stock says why: `highest_stock[X]` is how much X was on offer in open orders, and it was confirmed in game with The Sun vs Chaos (2,194 cards on offer, no chaos).
- For **Want A / Have B**, Available Trades need someone offering A, and Competing Trades need someone offering B.
- Internally, row `A:B` (receive A, give B) is made of orders offering B. So it has no orders when B's stock was 0 for the whole latest hour. A pair that traded earlier in the window but is **missing from the latest hour entirely** had no listings at all, so both of its directions count as having no orders. Prismatic Fossil vs Divine was the case that showed this. The job lists all these rows per league as `noOrders` in `rates.json`, taken from the latest hour only.

What the site does with them:
- **The ratio dialog** (opened from the trade pages): a box with no orders gets "no available trades" or "no competing trades" under it, worded for its column. The Market Ratios tables don't show it.
- **Steps:** a step that reads such a row gets the same tag under its Ratio.
- On a **main trade** step read by Available Trades, the route is Untradeable: there's nothing to fill.
- **Nobody else posting** (Competing Trades empty, as the game showed or the latest hour says): a Competitive step posts the only order. With no other orders to price it by, it asks the pair's **usual price**: what it traded at over the last 4 hours (`recentA`/`recentB`), else over the last days, else in the latest hour, as the game shows a ratio (two decimals). That's what players do by hand. When the orders on the other side (Available Trades) already pay that or more, posting there fills them at once, so the step is filled from them, as an Instant step. It's shown as any other step, with no tag; it has no queue, isn't thin (nobody else's stock to need) and fills at the pair's pace. A pair that hasn't traded has no usual price, and the route is Untradeable as before. Example: nobody selling Vivid for Chaos, and the pair trading 48,000 Chaos for 400,000 Vivid over the last 4 hours: selling Vivid posts at 1 : 8.33.
- **Read from the game:** an import that shows one list with the other box empty (§4.7) saves that box as read with no trades (Available alone with no banners is also what a hover without Alt shows, so there a Competing price still in use, read in the last 4 hours, stays: Alt was let go since): it counts as scanned (for 4 hours, as any scan) but has no price. A route that needs an empty Available box is Untradeable with the same tag (worded for the route's mode) and no steps; one that needs an empty Competing box posts the only order (above). The item's other routes are priced as usual: The Insane Cat, worth about 14 div, with Chaos buy orders at 300c and nobody selling it for Chaos, still lists its route buying it with Chaos. A later read with prices replaces it.

**Thin stock.** (A pair with a recent order book read from the game, §3.2a, goes by the book instead.) `rates.json` also gives each listed pair's latest-hour stock: `stock: [a, b]`, the lowest over the hour, i.e. what was on offer throughout. An Instant step needs at least **its own size** on offer behind the price it uses: the stock of what you **receive** must be ≥ what you receive. With less, the step is tagged "only N available", and on a main trade that makes the route Untradeable, tagged "not enough available". A Competing step posts its own order, so how much other players have posted at its price doesn't matter.

### 2.2 Lots

In the game, both sides of an order are whole numbers. A displayed ratio is therefore the rounded form of some whole-number pair, and trades fill in whole **lots** of that pair. What's left after the whole lots still trades, a hair off the price (§3.2).

To get the lot for a displayed ratio `(a, b)`:

```
x = max(a,b) / min(a,b)
n = smallest integer in 1..1000 such that round2( round0(x·n) / n ) == round2(x)
big = round0(x·n)
lot = a ≥ b ? (big, n) : (n, big)        // (lotLeft, lotRight)
```

`round2` and `round0` round half up, which is how the game rounds (confirmed).

Examples: `2.75:1 → 11:4`, `1:8.27 → 11:91`, `3.13:1 → 25:8`, `380:1 → 380:1`.

## 3. Calculation

### 3.1 Routes

Every route starts by spending the base currency, Chaos in Chaos mode (the default) or Divine in Div mode (§1), and **ends by receiving the same currency**. Each route can be computed two ways, and the UI uses the game's names for them:
- **Competing Trades:** post your own orders at the Alt price (Slow).
- **Available Trades:** fill existing orders (Fast).

Each page uses one of the two for every step, so there are 3 results per item per mode.

**In general** (`routesFor` in `js/calc.js`), a game has a list of **hub** currencies (`js/game.js`; PoE1: Chaos and Divine). Starting in hub S, with H any hub other than S, the routes are:
- S → Item → H → S, for each H;
- S → H → Item → S, for each H;
- S → Item → S, the **direct** route.

For PoE1 that's three routes in either mode:

| # | Div mode | Chaos mode |
|---|---|---|
| R1 | Div → Item → Chaos → Div | Chaos → Item → Div → Chaos |
| R2 | Div → Chaos → Item → Div | Chaos → Div → Item → Chaos |
| R3 | Div → Item → Div | Chaos → Item → Chaos |

Internally the routes are identified as `after:<hub>`, `before:<hub>` and `direct`.

**No step trades a currency for itself.** A route that would (X → X) is dropped. This only happens when the item is itself a hub (§4.1). For example, with a Div start and Chaos as the item, only **Div → Chaos → Div** is left (Div → Chaos → Chaos → Div is dropped twice over). With a Chaos start and Divine as the item, only **Chaos → Div → Chaos** is left. A hub item's extra is kept as that hub's extra (§3.3), never sold. Routes like these trade one pair both ways: with Available Trades they pay the gap between its two directions, with Competing Trades they earn it.

### 3.2 One leg

A leg receives `X` and gives `Y`, starting from `have` units of `Y` (whole number).

- **Slow** (post your own order at the displayed ratio): use row `X:Y` with lot `(p, q)` = (X per lot, Y per lot).
  `lots = floor(have / q)`, `receive = lots·p`, `give = lots·q`
- **Fast** (fill someone else's order): use row `Y:X` with lot `(p, q)` = (Y per lot, X per lot).
  `lots = floor(have / p)`, `receive = lots·q`, `give = lots·p`
- **Top-up:** what's left after the whole lots (less than one lot) still trades in whole units, rounded the way the order cap's rounded orders are (below): buying the expensive side, as many whole units as it affords at the price plus 0.005, paying that rounded up; buying the cheap side, all of it, for the price less 0.005 times it, rounded down. It costs under one unit of the cheap side, and the other side gets the hair. It joins the last order of whole lots when both sides still fit the cap, so it's one order to place. Example: 53,375 Vivid at 1 div : 2118.33 (lot 3 : 6,355) make 8 lots, 24 div for 50,840; with the top-up it's **25 div for 52,959** (shown in game as 2118.36), 416 Vivid extra. No step tag marks it.
- `extra = have − give` (in `Y`)
- The next leg starts with `have = receive`.

Whole lots match the displayed ratio exactly; only the top-up and the order cap's rounded orders are a hair off it, in the other side's favour.

**Order cap.** The exchange accepts at most **999,999** of a currency on either side of one order. A leg whose total is bigger than that is split into several orders of whole lots, each with no more than `floor(999999 / max(lotRecv, lotGive))` lots. The totals don't change. Gold is rounded up per order, and the drill-down lists each order. A lot that is itself bigger than 999,999 on either side (only very large prices with decimals: 250000.37 : 1 shows from 4,750,007 : 19 at the least) is traded in **rounded** whole-number orders instead, each within the cap. The game shows prices to two decimals, so the real price behind one can be up to 0.005 either way; the orders are rounded so they always go through whatever it is (filled at once in Available Trades, at least as good as the best in Competing), and the rounding falls on the cheap side, the big number, so it costs under one unit of it. Buying the expensive side: as many whole units as you have affords at the price plus 0.005, paying that rounded up, and the rest is extra (e.g. 3 Divine for 750,002 at 250000.37, from 900,000). Buying the cheap side: all of it spent, asking for the price less 0.005 times it, rounded down (e.g. 7 Divine for 750,001 + 750,001 + 250,000 in three orders). The same goes for a scanned order book's level (§3.2a), up to its stock. The step's Ratio gets a grey **rounded** tag (hover explains). Only a single unit over 999,999 (a price over the cap itself) can't trade at all. The leg trades 0, and the step says so.

### 3.2a Order books (Available Trades)

A pair imported from the game (§4.7, Import Market Ratios) also keeps, hidden, its **order book**: every Available Trades price read (up to 5, best first) with the stock on offer at each, in the currency you receive, and when it was read. The list's last row, the "worse than" row (the same price as the row before it, with an arrow: all the stock at worse prices), is kept too, as a last level **at that price**: in truth that stock is at worse prices and wouldn't all fill instantly, but it's taken as the worst price shown. A pair's Available Trades are the same orders as the reverse pair's Competing Trades (Want Chaos / Have Divine's Available list is Want Divine / Have Chaos's Competing list), so each list read is kept as its row's orders, the newest read of a row replacing the one before whichever list it came from: the order book here is that list. Nothing shows it and nothing edits it. While it's under an **hour** old and its best price is still the pair's ratio (the Expired tab's Clear All forgets it with an expired price), an Available Trades (Fast) leg on that pair fills **level by level**, as the game fills an order priced at the worst level it reaches:

- The levels are taken best first, each at **its own price**, in whole lots of that price, as many as its stock holds and `have` affords. A level with less than one lot on offer is passed over. The next level is reached only once one is used up. Where `have` runs out, what's left tops up at that level's price (§3.2), up to the stock left there.
- What's **entered** (the step's ratio) is the **worst level used**: in the game an order fills instantly only at that price or a more generous one; the better levels it takes fill at their own prices and the difference is refunded. What's **received** is the exact total of the levels, and the next leg starts from it.
- If every level read is used up with more to spend, **what's on offer is bought anyway** and the rest is the step's extra (unspent on a first step), with the profit or loss worked out as usual on what was bought. The book is the source of truth, so the step is never "not enough" and the hourly stock check (§2.1a) doesn't apply to it. (The "worse than" row says there's more on offer, but not at what price, so it isn't used.) Without a book (none read, over an hour old, or the ratio overridden), the hourly stock is the source of truth as before: too little marks the step "not enough" and the route Untradeable.
- The order cap still applies (orders merged as few as fit 999,999 on each side), and gold is per order as usual. Extras are valued at the best price's lot.

Example (no "worse than" row): 1 div buys 3500 at the best price (1 lot on offer), 3400 (3 lots), 3300 (1 lot). 5 div takes all five lots for 17,000, entered as 3300 : 1; 3 div take 10,300 at 3400 : 1; 7 div take the same 17,000 with 2 div extra. Competing Trades (Slow) legs don't use the book: they're posted at the most competitive price, behind the stock already there (§3.6).

### 3.2b Manual (a price typed in)

Each direction of a pair can have a **Manual price**, typed in (want:have, as entered in the game), one per direction and league, kept in this browser until it's changed or reset. It's typed into a Manual step's numbers (item pages, §4.2, and My Listings, §4.6) or the price window (§4.2), and it's the same everywhere: changing it in one place changes every Manual step on that direction, on every page (steps started or done keep the price they were started at). A step set to **Manual** posts your own order, as a Competitive one, at its direction's Manual price, whatever the scans say; with none typed yet it's at the Competing price scanned, else the estimate, and picking Manual sets the Manual price to that. It has no order book and no place in the Competing list. Its fill time is a Competitive step's (§3.6) at that price, with the queue counted only when the price is the scanned Competing price: at any other price nothing is counted ahead.

### 3.2c Estimated (a pair not scanned)

In Estimated Trading (§4.1, §4.2) and on My Listings (§4.6), a step whose price isn't scanned is an **Estimated** step: it posts your own order, as a Competitive one, at the pair's **estimate**, the average of its latest traded hour in `rates.json` (what traded of each side, `volA` / `volB`), as the game would show it (two decimals, rounded half up, the smaller side 1). Both directions of a pair get the same estimate. A pair has one only when that hour is one of the last 4 finished hours: with none, and no scan, a route through it is Untradeable, tagged "no estimated price". An Estimated step has no order book and nothing counted ahead of it: its fill time is a Competitive step's at that price with an empty queue (§3.6); the hourly stock doesn't limit it. What's left over (§3.3) is valued at the estimate too where it isn't scanned.

Estimates have no gap between buying and selling, and a thin market's average drifts from the others', so a route through estimates can show a profit that isn't there (measured in October 2026 on the owner's scans: the average was within 5% of the midpoint of the two sides 73% of the time, and a three-pair route of averages showed +713 Chaos on 1,000). The estimated tag and the Home card say they're only a guide.

### 3.3 Extras

The unspent base currency from the first leg is not a cost, so profit is measured against what was actually spent.

Whatever is left over after a later trade (less than its next step could use) is **kept as it is**: nothing is sold or converted. That's an item (the Chromatic a Div → Chromatic → Div route couldn't turn into a whole div), a hub other than the start currency (Divine partway through Chaos mode R2's Div → Item leg), or, rarely, the start currency itself, which simply counts towards the profit. The routes are only the trades of their path.

### 3.4 Profit

Profit is **in the start currency, plus what's left over**: `gain` = the start currency received on the last trade (and any of it left over partway) − what the first trade spent, a whole number; then each currency left over, as it is. Shown with icons, a space between, always in the same order: the hubs (Divine, then Chaos in PoE1; Divine, then Exalted in PoE2), then the item, whichever is the start currency (only it has a sign): `[div]+16 [Chromatic]6`, `[chaos]+312`, `[div]-1 [chaos]258`, `[div]1 [chaos]+312 [Chromatic]17`. The item page's line of what's left under the steps uses the same order.

For sorting it needs one number, `value` (in the start currency) = `gain` + what's left over is worth:
- a hub at its rate to the start currency, from the row converting it would use (units per lot);
- an item at what it would sell for into the game's **sell-to hub** (Chaos in PoE1, Exalted in PoE2) by §3.2 in the page's method, whole units only (so a few may be worth nothing), then that hub's worth; nothing when the game showed that row with no trades (nobody to sell it to, §2.1a).

Nothing of this is traded or listed; it only ranks the route. **Ranking value** (`rank`, in div) = `value`, converted at the start currency's rate to div (from the row a conversion to Divine would use) when it isn't Divine. Every result has a rank in div, so routes sort the same way whichever currency their profit is in, and a route is profitable when its rank is above 0 (so `-9c, 35 Chromatic` can be profitable when the Chromatic are worth more than 9c).

### 3.5 Gold

Every leg costs `ceil(goldPerUnit[X] × receive)` gold, where X is the currency **received** (confirmed in game). Gold is **shown only**. It never changes profit or ranking.

### 3.6 Fill time

- **Available Trades steps are instant** (fill time 0, shown as "instant"): they fill orders that are already up. Whether there's enough on offer is the thin-stock check's job (§2.1a), not the fill time's.
- **Competing Trades steps** wait for someone to take your order. Your order is posted at the most competitive price, so it joins the **queue** there: the orders already at that price fill first. The fill time is the queue and then the step, both in what the step receives (the queue converted at the step's price), ÷ how much of that currency fills orders on the step's side per hour: the row's **measured buying** when its scans have it (below), else a quarter (`SIDE_SHARE`) of what the pair traded **per hour over the last 4 finished hours**. A trade fills orders on one side of the pair or the other (someone taking Available Trades fills the Competing orders across from them), so only some of the pair's trades take orders like the step's, and the digests don't say which side each trade filled; and some of what's traded fills orders posted and bought between two scans, never in the queue. Measured from 400 minutes of scans of Divine ↔ Vivid Crystallised Lifeforce and Chaos ↔ Divine (October 2026), the orders listed were bought at 16% to 37% of the pair's volume per side (a quarter over all of them), and the sides weren't even: one took about twice what the other did. Counting half for each side, the owner waited about four times the fill times shown. The job writes those totals as `recentA`/`recentB`.
  - The queue is the stock at the best Competing price as read from the game with that price (§4.7), in what those orders offer (what the step gives): with Want Chaos / Have Divine and 27 on offer at 365 : 1, 27 div (9,855 chaos) fill before yours. A Manual step's queue is that stock only when its price is that one (§3.2b). It assumes orders at one price fill oldest first.
  - **Undercutting.** The market doesn't stand still: orders posted after yours at a better price fill before it (ones at your price queue behind it). So the queue drains at the pair's pace **less the undercutting**, the rate at which orders are posted ahead, in what they offer per hour, converted at the step's price: fill time = (queue + step) ÷ (pace − undercutting), with the drain never under half the pace (`UNDERCUT_FLOOR`): undercutting at most doubles a fill time, since the orders posted ahead are filled by the same buyers. A tenth made a fill time ten times as long, and turned Vivid Crystallised Lifeforce : Divine's 25 minutes into 11.4 hours on one new 398 div order. Example: 25 div for 9,500 chaos behind 25 div queued, at 95,000 chaos an hour filling its side (380,000 traded), is 0.2 h; with 125 div an hour posted ahead (47,500 chaos at 380 : 1) it drains at 47,500 chaos an hour: 0.4 h. Instant steps aren't undercut.
    - **Measured from scans** (`js/undercut.js`, `undercutRate`): every read of a row's orders (§3.2a) is kept for an hour (`READS_FOR`), and only that hour is used. Each read is compared with the last read compared before it, when it's 2 to 20 minutes older (`MIN_GAP`, `MAX_GAP`; reads closer than 2 minutes are the same orders read again, and are skipped; reads further apart start afresh): the stock it lists at a better price than that earlier read's best was posted ahead in between. The undercutting is all of that stock over all of that time, once at least 20 minutes have been compared (`MIN_SPAN`); before that it isn't measured. It takes at least 3 comparisons that found stock ahead (`MIN_UNDERCUTS`): with fewer it's none, as one or two new orders are additions to the queue the read already counts, not a flow (one 398 div order seen once in 22 minutes was taken for 1,100 div an hour). Example: Chaos : Divine read at 0, 8, 16 and 24 minutes, each read listing orders ahead of the one before's best (4 div at 378 : 1 ahead of 380, 2 at 377, 6 at 376): 12 div in 24 minutes, 30 div an hour. It sees only the 5 prices the list shows, and orders posted and filled between two reads, or taken down, don't show: it's a lower bound.
    - **Measured buying** (`js/undercut.js`, `boughtRate`): the same reads, compared the same way, also show how fast the row's orders are bought: the stock gone from prices still listed, and all of the stock at prices better than the best one still listed (orders fill best price first), in what those orders offer per hour. With no price still listed, the prices better than the last one shown count (a full list pushed down by better prices loses its bottom prices off the 5 shown); a shorter list shows everything, so all of them count. Prices gone from further down than the best one still listed were taken down, not bought. It needs 20 minutes compared (`MIN_SPAN`) and at least 3 comparisons that saw stock bought (`MIN_BUYS`); otherwise the row isn't measured. It's converted at the step's price and takes the place of the pair's pace, with no undercutting taken off it: it was measured with the orders posted ahead already in the list, so taking them off counts them twice. With them taken off, a 47,150 Vivid order for Divine, in an hour when Divine rose from 1,840 to 2,141 Vivid (every new best price counted as posted ahead), showed 2.3 h and filled in 10 minutes. Orders posted and bought between two reads don't show, and a taken down order at the top looks bought.
    - **Rows not measured:** a row without its buying measured uses the pair's pace (a quarter of what it traded), less its undercutting when that's measured; with neither, its fill time is the queue and the step ÷ the pair's pace. So fill times make sense before anything's been scanned.
    - **Read history, for analysis:** every read is also kept for 2 weeks (`HISTORY_FOR`) in the browser's IndexedDB (§7), for retuning these numbers and for prices by hour of the day and day of the week. Nothing here uses it; `?debug` saves it when watching ends (§4.7).
    - A step whose fill time counts measured buying or undercutting says so on hover: "Paced by your scans: about 40 Divine Orb bought an hour" or "Counts orders posted ahead of yours: about 500 Divine Orb an hour".
  - A pair with no trades in that window, or with no data, gives no fill time ("—").
- **Per route:** the steps happen one after another, so a route's fill time is their sum (what's left over isn't traded, so it takes no time), unknown when any step's is. In practice that's the sum of its Competing steps, so a route whose steps are all Available is "instant".
- **Display:** "instant", "< 1 min", or a rough estimate with a "~" in front ("~25 min", "~3.2 h"); "—" when unknown (no recent trades, or no data). The home page warns that fill times are very rough estimates.
- **No time limit:** a route is listed and ranked by its profit however long it takes, with its fill time shown as it is and no warning. A Competing step whose pair had **no trades in the last 4 hours** has no fill time ("—"), and nor has its route (so no profit per minute either); it's tradeable all the same, with no tag and no red.
- **Shown:** per step in the steps table's **Fill Time** column, on each route box ("· 25 min"), and in the summary's **Fill Time** column.

## 4. Pages

The site has one set of colours, dark (a near-black page, its panels a shade lighter, light text, an amber accent), whatever the system's light or dark setting (`color-scheme: dark`, so the browser's own controls are dark too).

### 4.1 Trade Recommendations (`#/trade-recommendations`): Competitive, Instant and Estimated Trading

Each summary page has a **search box** (by item name) and up to **three tables** with the same columns:
1. **Profitable:** the route makes a profit and can be done. It shows "None right now." if empty.
2. **Unprofitable:** a loss or break-even.
3. **Untradeable:** an Instant trade has nothing, or too little, on offer to fill (no or thin available trades, §2.1a), or a price is missing (in Estimated Trading, no scan and no estimate). That's all: nobody else posting (§2.1a), little stock from other players behind a Competing price, a slow route or a pair with no recent trades doesn't make a route Untradeable. A route the starting amount can't afford (it needs more than that for one unit of some trade) isn't listed in any table (§4.2).

### 4.6 My Listings (`#/my-listings`)

- **What it's for.** A route's first Competing step can take half an hour or more, and while it waits the market moves: its own fill time goes stale (newer, better orders go ahead of it) and the later steps' prices change. The game lets you have many orders up at once, alike or not, even on the same pair at different ratios, so each route you start is kept as a **listing**, the game's word for a posted order, and followed with every scan.
- **Adding one.** Every route box with steps (§4.2) has an **Add to My Listings** button at its bottom right, under its steps (where a listing has Delete and Mark As Completed). It adds the route as it is right now: the item, the start currency and amount, and each step's Competitive or Instant choice. It can be clicked any number of times: the game takes the same order as often as you post it, and each click is another listing. Left of the button, once there's at least one, is how many active listings this route has (the same item and path, in the selected league, whatever their amounts), as a number in a pill linking to My Listings (hover "2 active listings of this trade").
- **The page.** In the header nav after Trade Recommendations (§4.1), with "My Listings (N)" counting the selected league's active listings. No page heading and no Starting Amount (each listing has its own). It has two tabs (styled like the item page's): **Active (N)** (`#/my-listings`, the default, which the nav opens) and **Completed (N)** (`#/my-listings/completed`), N counting the selected league's listings on each. The header's League dropdown picks whose listings are listed. Newest first on both. With none active: "Nothing listed for <league>. Use Add to My Listings on a trade's page to follow it here."; with none completed: "No completed listings for <league>." (muted, as Trade Recommendations' empty message). The Completed tab has, under the tabs at the left (in line with the page), **Clear All**: red, disabled with no completed listing in the league, it asks "This removes N completed listings for <league>. Are you sure?", with **Yes** or **Cancel**, and then deletes them. Active has none.
- **Each listing** is a route box like the item page's (§4.2). Just above it, a line in small type: **Start** (no colon) and the amount the listing started with, in its starting currency (both bold: **Start [chaos]10,000**), then, a little apart (1.75rem), **Projected** (bold, no colon) and the profit its route showed when it was added, in the same format as the line's (`Start [chaos]10,000   Projected [div]+1 [chaos]121`; neither ever changes) on the left; on Completed, then, as far apart again, **Profit** and the profit it made, its steps at their own prices (the listing's line's profit, coloured by its sign as Projected is), and when it was added, the date and time, "2026-10-23 @ 02:39pm" (local time, on a 12-hour clock with two-digit hours, am or pm right after the minutes; on Completed, then when it was completed: "2026-10-23 @ 02:39pm - 2026-10-23 @ 03:12pm", with a little more room either side of the dash; in bold) on the right. In the box, its line and its steps table with the item page's columns (#, Want, Have, Ratio, Fill Time, Gold Cost, Type) and, at the end of every row, a **play button**, a **cancel** (a filled square, a media stop: the order taken down early) and a **check** (1.5rem each), in the order they happen. They keep their place on every row and every listing: their column hugs the table's right edge. The header's headings, and each row's cells, all sit on their bottom line. Want and Have are as wide on every steps table (10.5rem), so the columns line up from one listing to the next. **Type** is the item page's dropdown (§4.2) on waiting steps: Competitive, Instant, Manual, in that order. Changing it works that step and the ones after it out again, from that way's latest scan, and is kept with the listing. A waiting step whose price isn't scanned (never, or over 4 hours ago, §4.3) is an **Estimated** step (§3.2c), whatever Type it was given, with the estimated tag; its dropdown holds just **Estimated** and **Manual**, and in place of its play, cancel and check buttons it says "Cannot trade" (muted, small; hover "Set its Type to Manual and type the price the game shows first"); nor does "Similar order detected" show for it. A Manual step with no Competing price scanned has the same dropdown (Estimated there is kept as Competitive). When its pair is scanned again it's back to its Type (a step added from Estimated Trading as an Estimated step is Competitive).
**Manual** trades at its direction's Manual price (§3.2b): scans don't change it, and it's the same as on item pages and in the price window. Picking Manual where there's none sets it to the price the step had. Its Ratio cell opens no dialog. Both numbers sit on a shaded background (the accent colour, darker on hover; hover "Change"), and clicking one turns it into a box with the number selected: Enter, or clicking away, takes what's typed (any number, rounded half up to two decimals); Esc, a blank or 0 leaves it as it was. In the scan tag's place is a **reset** button (hover "Back to the Competing price"), which sets the Manual price back to the pair's latest Competing price, or with none scanned to its estimate (hover "Back to the estimated price"), greyed out while the price already is that one or there's neither ("No Competing price scanned"). Once started, a Manual step is like any other: its ratio the usual button with its scan tag. On started and done steps it's plain text (Competitive, Instant or Manual).
- **A step's three states.** Each step is **waiting** (not started), **in progress** (its order is up in the game) or **done** (filled). At most one is in progress, and the steps go in order: each step's play button, then its check.
  - **Waiting** steps are worked out as on the item page, from the latest scans: ratio, amounts, gold and fill time all follow each scan. Each starts from what the step before it receives (the listing's start amount for step 1): no step's Have is typed. Their Fill Time is the step's fill time now, as on the item page. Amounts copy on click, as every amount does. Every ratio comes from scans.
  - **Started** (its play button): its order is up in the game. It's frozen as it was when it was started (its ratio, Have, Want, gold and how it's traded; no dropdown), and only its **Fill Time** follows the scans, worked out at its ratio from **what's ahead of its order** in its row's list as last read (§3.2a): all the stock at better prices (orders posted after it, undercutting it, fill first), and at its own price, what was there when it was started (`queue`; orders at one price fill oldest first, so later ones are behind it) as far as the stock there now, less the order itself, still holds it (a list read before the step was started doesn't have the order in it, so nothing is taken off). The queue may or may not hold the order (play pressed before or after a scan showed it): either way the others ahead come out the same. Taking the order off the queue instead counted none ahead whenever play was pressed before the order showed (Vivid Crystallised Lifeforce / Divine Orb: 9, 10 and 20,064 ahead, each read as 0); with its price off the list (worse than the 5 shown), everything shown; with no list read, the stock at the pair's best price. It counts down from the pair's latest scan (or from when it was posted, below, if later). Counting only the stock at the best price, a step undercut by a 10 div order showed about 6 minutes on every scan with 140 div still ahead of it at its own price. Its **Ratio** has the age tag of its pair's latest scan beside it, as every step's has.
  - **Done**: the step has filled. Its ratio and amounts stay as they were when it was started (its Ratio with the age tag of its pair's latest scan, as every step's); its Fill Time is how long it took, from when it was posted to when it was marked done (exact, so with no "~": "< 1 min", "25 min", "3.2 h"; hover "How long it took"), and its check is blue.
- **An order seen without its play button.** When a scan of the next step's list (Competitive or Manual; it must be waiting and the step before it done, or for step 1, the listing added) shows the stock at its price risen by 95% to 105% of its order since the scan before (at most 20 minutes apart, the later one after the step became next), a line under the step asks "Similar order detected. Was it yours?" (green, at the right, joined to its step's row) with **Yes** and **No**. Yes starts the step as its play button would, timed from that scan; No hides the line for that step for good. Pressing play hides it too. Over the owner's first 7 orders (October 2026), 4 rose by exactly their order between two scans; the other 3 had partly filled before the next scan, and need the play button. A wider range (from half the order) would have caught 2 of those but also someone else's similar order; nothing is ever started without Yes.
- **Cancelled partway.** An order taken down before it all traded (overtaken by undercuts, say) is the started step's **cancel** (hover "Cancel this step"). It opens a small box beside the button, floating over the page so nothing moves (level with its row, just right of the button; to the left of the row's buttons when there's no room on the right): small type, headed **Cancelled** with a small × at its top right and a faint line under both, then one line: the step's Have icon, a narrow box and **Remaining**, how much of its Have wasn't traded. Enter, or a click outside the box, takes what's typed (with nothing typed, a click outside just closes it); the × or Esc closes it, the step as it was. More than the step had isn't taken: the box stays, outlined in red (hover "At most 25"). With **none remaining** it's the check (done); with **all of it remaining**, nothing traded: back to waiting, as its play button does. In between, the step is **done for what traded**, at its own price (25 div posted for 50,000 Vivid, cancelled with 24 div remaining: done for 1 div and 2,000 Vivid, rounded to whole units), and a **new step is inserted after it**, trading what remained the same way (Have the 24 div, Want Vivid) at the latest price, waiting for its own play button. The cancelled step's row stays as it was posted (its Want, Have and gold, which was paid when it was posted), with how much of it filled after its Have, on the same line and never wrapping: "[div]25 (1 filled)". The step after them has what both bought together, and the profit counts each at its own price. The inserted step is a step like any other (it can be started, cancelled in turn, or have its Type changed), and while it waits, its cancel (hover "Remove this step: back to the order before it") removes it and starts the cancelled step again with its whole order, as the cancelled step's check does (hover "Done: click to put it back to started").
- **The buttons.** Each is an outline until it's on (its icon in the text colour, whether or not it can be clicked: never greyed out), then filled in; one that can be clicked and isn't on fills faintly, its outline darker, under the mouse. Filled in: the play button green once the step is started (or done), the check blue once it's done (not red, which reads as cancel); each is disabled where it can't be clicked. A waiting step's play button (hover "Start this step") starts it, once the step before it is done (step 1 any time; before that, hover "Finish the step before first"): its ratio, Have and Want are kept from then on. The started step's play button (hover "Started: click to put it back to waiting") puts it back to waiting: worked out from the latest scans again, at once. The started step's check (hover "Mark this step done") marks it done, fixed as it last stood; the step after it waits for its own play button, so its kept ratio dates from when it's actually posted. The last done step's check (hover "Done: click to put it back to started"), while the step after it isn't started, puts it back to started (its time counting on from when it was posted, not from the click). **When a step was posted**, for its times: when its play button was clicked, unless it was marked done within a minute of that (`LATE_PLAY`): then play was clicked late, as the order filled or was taken down, and it's when the step before it was marked done (step 1: when the listing was added). Play is often clicked late (a step played and checked 2 seconds apart showed "< 1 min" for an order taken down for taking too long), but a step isn't always posted as soon as the one before it is done (one went up an hour later, as its scans showed: timed from the step before, it showed 104 minutes for under 41). When every step is done, Mark As Completed is enabled.
- **The listing's line** is the line of the item page's route box it came from (§4.2), in the same order and format, but a listing is never dimmed, whatever its profit or steps (it's started; its line and steps' tags say what's wrong): the profit as the item page works it out (§3.4), counted from the listing's start amount, steps in progress or done at their own ratios and the rest live, with what's left over in the same way (what a step bought that the next one doesn't spend, whatever that one's Have); the fill time; profit per minute from that fill time; the gold; and the route's path on the right. On **Active**, the fill time is the whole trade's as it now stands: each done step as long as it took (from when it was posted to when it was marked done), the step in progress as long as it's taken since it was posted plus its Fill Time, and each waiting step's fill time now. On **Completed**, it's how long the trade took: every step is done by then, so it's their times added up. It never re-sorts while the page is open.
- **Delete and Mark As Completed:** at the bottom right of every active listing, under its steps, Delete then Mark As Completed. **Mark As Completed** (green, filled in; disabled, with the hover "Finish every step first", until every step is done) moves it to the Completed tab, where it's a snapshot: the same box with no step buttons, and under it Delete then **Mark As Active** (an outline button), which puts it back on Active as it was. **Delete** (red outline) asks "This deletes the listing. Are you sure?" with **Yes** or **Cancel**, just under the buttons, then removes it from either tab. Market Ratios' Clear All doesn't touch listings (they're your orders, not scanned prices).
- Trade listings are kept per league in this browser (§7) and never exported.

### 4.7 Reading prices from the game

Import Market Ratios (§4.3) reads the game's market ratio hover box from the shared game window (each frame of it a "snip" in the code), which lists the best prices and the stock at each: **Available Trades** on hover, and **Competing Trades** under it with Alt held. The ratio dialog (§4.2) only shows a pair's prices; it has no import of its own. It all runs in the browser: nothing is uploaded, and there is no third-party code. On both games the reader knows Path of Exile 1's font, which PoE2's exchange shares; only finding the window differs (below).

- **Watching the game.** A read of a whole window takes a tenth to half a second with the hover box showing, and well under a tenth without it. Reads run in a worker, the price reader (`js/reader.js`, started the first time the game is watched, with the catalog's names; it loads `data/glyphs.json` itself), so the page never waits on one: each frame is handed over as a bitmap (`createImageBitmap` of the shared video, about a millisecond), and the worker copies its pixels out, finds the window, the lists and the names, checks a reading waiting on its second read (below), and answers with what it found; the page decides what the reading is worth. The reader shares each read with a second worker, its helper (the same script, started by the reader): the helper gets its own copy of the frame (a second bitmap) and reads Competing's rows while the reader reads Available's, then the I Have name while the reader reads I Want (matching a box's text against the catalog takes 20 to 120 ms a name, as long as a list). Both find the window themselves; the reader joins the rows and makes the lists of them as one read would. Over the 31 test frames with the window the lists and names read are the same as one worker reading it all, and a read takes 27% less in Firefox (6.1 to 4.4 s in all) and 20% less in Chrome (4.8 to 3.8 s); a frame showing only one list gains nothing. When a reading waits on its second read, the helper gets the frame only once the crops check (below) has found it changed. Without the helper (it can't start) the reader reads it all itself, and so it does once the helper dies or takes over 5 seconds to answer (`HELPER_WAIT`; a read takes a second at most): it's let go, and the read waiting on it carries on alone (with a stuck helper, measured: that read took 5.1 to 5.3 s, the next ones as long as usual). Measured on 62 frames (41 test, 21 of the owner's): the page was held up 39 ms in all in Firefox (the longest 1 ms) and 1 ms in Chrome, against 11.7 and 10.5 s when the page read them itself (the longest 442 and 473 ms), the same lists and names read, and each read done 9% later in Firefox and 5% sooner in Chrome. Handing over the pixels instead, copied in the page, held it up 162 and 228 ms, and on the owner's machine that copy alone takes 30 to 45 ms. One frame is read at a time: the next look waits for the read. The lists are read only within the game's Currency Exchange window, found by its title-bar buttons. A frame that misses the window within 15 seconds of one that showed it (`WINDOW_KEPT`; the game redrawing it, say as Alt goes down) is read where the window last was, as quickly as any read. Without the window for longer, nothing is read, and until something is imported the import window's status says "Can't see the Currency Exchange window." A frame is never searched all over for the lists: on full frames that took 1.2 to 6 seconds in Firefox (4.3 to 6 on the owner's 2416 x 1431 frames) and 1.2 to 8.7 in Chrome, during which nothing else is read, against 0.1 to 0.75 seconds for a read from the window; it found the lists less often than reading from the window, and over 37 full frames (the owner's 10 debug frames among them) the window was found in every one, so it never found lists the window missed. The window is glanced at every tenth of a second (`LIVE_GLANCE`), shrunk to 96 x 54, and read only when over 1.5% of that changed by more than 12 grey levels since the last read (a hover box appearing, or Alt pressed); a window that hasn't changed would read the same. A cursor isn't enough to count (on the owner's 2335 x 1284 frame it changes 23 to 34 of those 5,184 pixels, two places 46 to 68, under the 77), so after a read that saw the hover box (a row that reads at a list's place with the column heads over it, or any row there with the heads plainly showing, 0.6 or more: lists' places 0.75 to 1.00, an idle window's ratio field or order cards 0.38 at most) but not both lists, nor one with the other shown empty (the cursor over a list, say), the next look reads again whatever it sees, until a read has both lists, one with the other shown empty, or no hover box. Without the hover box nothing is read again unchanged: the window's ratio field, with no box, reads as one unread row, and reading it again every look took 0.8 to 1.1 s each on the owner's machine. Once the game's window has been found in a frame, only it is glanced at (from its buttons, 5% of their spacing wider each side, down to 0.75 of the spacing below them): the game moving round it is no change; without it, the whole frame is. After each read it rests half as long as the read (a tenth of a second at least), and not at all while a reading waits on its second read. That second read is often skipped: the reading keeps the pixels it rests on (the two name boxes and each list's first row), and a later frame whose pixels there differ by at most 6 grey levels on average reads the same, so it confirms the reading at once (a cursor or the game moving elsewhere in the window doesn't matter; a new stock in a first row does, and is read as usual). Scaling big frames down before reading was tried and isn't done: at some scales the resized text read nothing, at others a name fell short of certain. The preview (`drawPreview`) is the shared video itself, at most 560 px wide (`PREVIEW_W`), with rounded corners and no border, so it plays as the game does however long a read takes (it's checked every tenth of a second, and put back and played after the panel is drawn again). Holding Alt is taken in about a second (simulated at 2384 x 960 and 2544 x 1353 with the scenery moving). **The scan sound:** whenever Import Market Ratios fills in a pair with new prices, or a pair shown again after its price box had gone, the page plays a short double click, since the game usually covers it: two clicks 90 ms apart, each two pitches (1.3 and 0.7 kHz) dying away within about 5 milliseconds, too short to hear as a tone, peaking at 0.5 of full volume (tuned by ear against other tabs' sound). It's made by the browser (Web Audio), with no sound file. Browsers only allow sound after a click on the page, so the record button's click readies it; without Web Audio there's no sound. If sharing is cancelled at the browser's prompt or stopped from the browser's own control, the window stays, saying why on its status line: "Sharing was cancelled.", "The shared window can't be shown." (with a warning sign, a triangle with "!", after it) or, in red, "Couldn't load the price reader.", with the record button to try again. Nothing is recorded or uploaded: frames are read in the browser and dropped. **Troubleshooting:** with `?debug` in the address (e.g. `rainofchaos.app/poe1?debug`), the site also loads `js/debug/watch.js` (only then: app.js just calls it when it's there, at each look, read and end of watching). It adds nothing to the window. - **Reading.** A frame is read by the game's window where it's seen (`findAll`, `js/rows.js`, below): the window's buttons give the place and the scale, each list is read slot by slot from its place, and each row by the row reader. A frame with no window found isn't read (above). **The status line**: every message about what the panel is doing or what happened (what watching has found, why watching stopped, and errors; each ends with a full stop or an ellipsis) is its first line, in one place and one style: at the top of the panel, under the steps when they show. It shows only when something's wrong: errors, red after an error icon (a circle with "!"), "Can't see the Currency Exchange window." among them; and the warning (bold in the accent colour, with its sign). The rest ("Imported prices for…", "Waiting for price info.", "Sharing was cancelled.") are kept for screen readers only, taking no room.
- **The window** (`findWindow`). **Each game has its own window style**, kept apart (`WINDOWS` in `js/snip.js`, named by `window` in `js/game.js`): how its buttons are found and where things sit below them (`AT`, `AT2`). A page only looks for its own game's window, so neither game's rules can mistake something in the other's screen for a window, and a new look is a new entry. **Path of Exile 2's** buttons are dark discs with light glyphs ringed in gold: the "x" on dark red, found by its red (`r` at least 35 and over 2.5 times `g` and twice `b`; the red is about 0.74 of the button), its arms light either side; the "i" 21 to 27 buttons to its left on its line, a light upright stroke with nothing light either side (its middle where several columns score alike); the same dark title bar between them (over 75%). Its hover box is the same size as PoE1's but 0.068 of the spacing higher (it covers the Market Ratio line): Available's first row at 0.134, Competing's at 0.407, the box from 0.042 to 0.632; with no Competing trades it's assumed to move the same way (0.096, not yet seen). Found in about 30 ms, the PoE2 frame reads in about 0.3 s by the window, where the whole-image search took 4 to 14 s. **Path of Exile 1's**: the Currency Exchange window's title bar has two round orange buttons, an "i" at the left and an "x" at the right, the same size, level, and 23 to 26 button widths apart (24.4 in every screenshot), with the dark title bar between them (over 75% of it dark; a skill bar's orange icons have more icons between them, at most 66%). They're found by colour (warm pixels, gaps of 2 closed: the glyph splits a disc) in 10 to 30 ms. Warm is by proportion, not level (red at least 60, over 1.4 times green, green over 1.2 times blue, blue under 0.45 of red), and a disc's warm pixels need fill only over 0.1 of its box: the "x" is redder and darker than the "i", and in one 2277 x 1183 capture filled 0.144 (the test frames 0.154 to 0.255), so a fixed level and a 0.15 floor lost it. The game's brightness setting moves the whole frame: every PoE1 test frame's window is found 40% darker, 50% brighter, and at gamma 0.7 and 1.25 (at gamma 1.4 the orange washes out of some). Each button is also told by its dark glyph, in the inner third of the disc (`buttonIs`): the "i" is an upright stroke, dark down the middle and clear at one side at least above and below the middle; the "x" is dark at both sides there, where its arms are. Dark is under half the pair's light (the lighter button's 90th percentile of luminance over its middle; the "x" is the darker, and against its own light its arms come out too light), so brightness moves glyph and orange alike (in every test screenshot the "i" has a side at 0.33 or under and the "x" both at 1). A pair must be an "i" on the left and an "x" on the right. Something else orange beside the window once passed for a button: with the stash and the inventory both open on a wide screen, the window's own "x" taken for the left button and a socket in the inventory for the right, over a darker bar than the title bar's. Every pair that passes all the checks is a candidate (`findWindows`, at most 6, the darkest bar between first), and the lists are looked for at each in turn: the first whose hover box gives rows is the window. A pair with no room below it for Available's first row (0.202 of its spacing) isn't the window: at 1280 x 960 the HUD's orange Menu arrow and (i) button, at the foot of the screen, are as far apart with a dark bar between them, and darker than the title bar, so they were once taken for it, and watching (which never searches) read nothing. Their spacing need only fit a button size between the two found (at least 23 times the smaller, at most 26 times the bigger): either can come out off, the "x" smaller when it's redder and fewer of its pixels are warm enough, one bigger when it touches something orange; against their average, a real window's spacing once came to 26.4 widths. The distance between them, the **button spacing**, measures everything else: the window and the hover box scale with it exactly, at every size (800 x 600 to 2544 x 1353). Available's first row is 0.202 of it below the buttons, Competing's 0.475, rows 0.0322 apart; with no Competing trades at all the box has no banners and Available's first row is at 0.164 (one capture). The hover box is cut out (0.38 of the spacing wide, centred, from 0.11 to 0.70 below the buttons) and only that is read.
- **Rows by their slots** (`readSlotRows`, `entryInSlot`). Rows are placed by the window, not by anything in them: each list is read from its place (below), one row spacing down at a time, and each slot's strip is cut from the gap above its row to the gap below. A row's text is about two thirds of a spacing (digits 0.50 to 0.55 of it, commas a little under the line), so a row placed 0.15 of a spacing off still loses none of it; the window places every row within 0.07 of first + k spacings. The line a row's digits stand on is the highest bottom among its digit-tall shapes, leaving out any cut by the strip's side (a sliver of the player's order card beside the box, its ratio a few pixels higher, once set it 3 pixels high and the row went unread: Vivid Crystallised Lifeforce / Chaos Orb, 2366 x 1242) and any starting over 4 digit heights right of the stock's centre (`TEXT_REACH`: 8-digit stocks end within 3.1 of it over 485 test rows; a streak in the box's texture 5.3 digits right of it, 4 pixels higher than the digits, once left Competing's fifth row unread and the list with it: Stacked Deck / Divine Orb, 2347 x 1332). Across the row: the game centres every stock on one column, 0.0466 of the button spacing right of the window's centre (`STOCK_AT`; within 0.002, about 2 pixels, on 90% of 487 rows from 800 x 600 to 2564 x 1406, both games), so the stock is the run of digits from the one nearest that centre out to the right while they're under 0.9 of a digit apart, and its left edge about as far left of the centre as its right edge is right of it: at the widest gap with no comma or point at its foot (the space before a stock never has one) that's at least 0.33 of a digit wide (`SPACE_MIN`: gaps within a number are 0.31 at most; the space, even before an 8-digit stock, 0.35 or more) and has the stock starting within a digit of that mirrored edge. A few pixels' error in the centre once put the edge inside "1,645,839"'s thin leading "1,", which was dropped, the stock read 645,839 and its list, off-centre, went unread (Divine Orb / Dead Man's Sulphur, 2335 x 1284); the widest gap, not the nearest, because in small text a single pixel is a third of a digit's gap. A row whose space is narrower than the usual 0.7 of a digit is read with it as narrow as 0.25 ("1 : 42201  1,645,839" leaves 0.61, "> 1 : 42000  78,397,883" 0.41). Stocks are drawn dimmer than ratios (0.86 of their brightness, median over 614 rows) but not reliably: from 0.70 to 1.16, and on half the rows a ratio digit (a thin 1) is no brighter than the brightest stock digit, so brightness doesn't tell them apart. The ratio is the digits left of the stock (the space before the stock is 1.7 to 4.8 digits), back while each is under 0.9 of a digit from the next, but for one wider gap of up to 1.9: the colon's. The colon is the middle of that gap; its dots needn't be seen (at 800 x 600 the upper dot isn't a shape at all). Specks under the line and the box's own edge lie past a second wide gap and stay out, and the strip starts at 0.15 of the button spacing left of the window's centre (ratios reach 0.128, the box's edge is at 0.146). An arrow ("worse than") is a shape before the ratio, shorter than a digit and centred at mid-digit height, and not cut by the strip's side (a sliver of the box's left edge once read as one, ending Competing after two prices: Dead Man's Sulphur / Divine Orb, 2347 x 1332); a row that doesn't read with one is read again without (a speck taken for an arrow). Ratios don't line up by either end or their middle ("1 : 7" ends short of "1 : 6.90"), so only the stocks place anything across the row. Measured against reading rows by their colons (found anywhere in the box as two small dots, at three brightness cuts, with the line reader when under three were found), over 41 test frames and 31 of the owner's: the same lists, empty sides and `hover` on all 72, and as quick (9.3 s against 9.5 s for the 53 with a hover box; 37 against 46 ms for an idle window's median). Colons had been found too dim, or false ones inside a smaller ratio ("328.89"), or in the player's order listings, and strips set from a colon found a few pixels off cut text.
- **Reading a row** (`entryInSlot`, `fit`). The row reader keeps one large, sharp example ("master") of each character, taken from the game at its largest (`size-full.png`) and shipped in `data/glyphs.json` (`rows`), draws them at the row's size (the row spacing gives it, finer than a pixel), and finds the string the row's format allows ("X : Y  Z", one side exactly 1, a point only before a ratio's last two digits, the stock's commas every three digits from the right) whose characters, placed along the row, best redraw it. Each row's strip is its slot (above), with everything outside its ratio, arrow and stock blanked; the colon's place, the middle of the ratio's wide gap, is given to the fit. Before fitting, the strip loses the panel's lines between rows (pixel rows lit across most of it), anything taller than any character or running into the strip's edge (a mouse cursor beside the row, a header's letters), and is levelled so no strip stretches its contrast past 90% of the box's (a row as bare as "1 : 1  1" would otherwise turn faint texture into shapes). Once something is taken out, the strip is levelled again from what's left, still never past 72% of the box's contrast (0.8 of that 90%): a bare row right under its list's header ("3 : 1  1" under Competing's "Ratio  Stock") would otherwise have its texture as its brightest part. The fit is scored only under the characters, not the gaps. A place where the strip's ink (from running totals of it) is too little for a character to pass is ruled out before the character is compared there, and the format's steps are worked out once per row: with one example of each character, that reads the 58 frames measured (39 test, 19 of the owner's) in half the time of comparing everywhere with two examples each, to the same lists, every row as sure within 0.003. A row is **sure** when, for each digit, the best reading of the stretch round it (three characters before to two after) with that digit forbidden there costs clearly more (0.09 of the digit's ink; over the test screenshots no wrong row was surer than that). A point the usual reader saw on its own with none placed, between two digits of one number, leaves the row unsure; a speck that starts more than 0.2 of a digit below the line (`LOW_MARK`) isn't a point (points and commas start from 0.33 above it to 0.07 below over the test screenshots; the box's texture leaves specks from 0.13 below on). A comma too faint to see may be read across; the text gets it back from the digit count. A point must be seen ("2.90" and "290" are both prices). Digits may sit up to 12% of a digit off the line (old-style 3, 4, 5, 7 and 9 hang below it; 6 and 8 rise above). Long ratios (5 characters or more: "366.50", "2500.10", "65000") are drawn smaller (0.82): the reference's own small ratio gives small masters (its "366.50": 0, 3, 5, 6, the point and the colon), two more frames' small ratios give the small digits it lacks (2294 x 1241: `small-eights-window.png` 2, 7, 8 and 9, `small-four-window.png` 4; size-full's 8 shrunk read "158.68" right but too unsurely, 0.085), and the full-size masters drawn at 0.82 are offered too. A ratio's characters are small masters when one of its numbers has 5 characters or more, the game's own rule. A smaller ratio is level with the stock at the top, not on its line, and the strip is cut on the ratio's line, so a row read with one is read again with the full-size characters (the stock) lower by 0.18 of a digit, and the better reading kept (at 2017 x 925, "6,500" beside "2166.67 : 1" read 15,500 with its 6 two pixels off). Smaller characters are only tried left of where the stock starts, and that second read redoes only the stock's full-size characters, the smaller ones kept from the first: the same reads, faster (a 2294 x 1241 frame with small ratios, 900 to 550 ms in Firefox). A shape counts as a digit when it's at least 0.62 of a digit tall: an even longer ratio ("1 : 16666.67") is drawn smaller still, its "1" two thirds of a digit tall, and was once left out, so the row (and its list) went unread. The stock is told from the ratio by its centre (above). A stock never starts with 0 (a row whose stock is partly under a cursor read "0" for "50,000"; it's unread now).
- **Lists top-down** (`groups`, `walkFrom`). Each list is read slot by slot from its first row, which the window places: Available's bare place first (a bare list's second row is near the place under the banner), then Available's under its banner (also Competing moved up), then Competing's. A first row is a row read within 0.3 of a spacing of its place, in no other list, with the column heads ("Ratio" and "Stock") over it: compared, slid a little up and down, with a reference taken from each game's window (`heads` in `data/glyphs.json`, PoE1's from `size-full.png`, PoE2's from its frame); lists' first rows match at 0.34 or more (a cursor over the heads takes some away), the window's own ratio field ("1 : 5.96", between the I Want and I Have amounts, just above the bare place when there's no hover box) at 0.07, so 0.2 decides. Measured over 38 test frames and 19 of the owner's: first rows within -0.21 to +0.10 of a spacing of their places, and every row within 0.07 of first + k spacings (the spacing from the window). Each slot a spacing below the last then holds the next row; or it's empty (the 97th percentile of its grey levels over its median, across the list's width, under 40: a row's text is 52 or more, the panel alone 31 at most), and the list ended at the slot before; or it has text that doesn't read (a cursor, say), and the list isn't read, rather than cut short into a list that would look real. A slot whose only shapes are cut by the strip's side holds no text: the box's left edge, lit in the slot under Competing's last row, once left the list unread (Divine Orb / Tailoring Orb, 2347 x 1332). The "worse than" row is a list's last; after 5 prices only a row that reads is taken (a "worse than" row that doesn't read leaves the 5 prices, without the rest's stock). Nothing outside the slots joins a list, nor is it read: each place's first slot is read, and the slots under it only when a row reads there, to an empty slot, an unread row or the "worse than" row (a slot read for one place isn't read again for another), so the player's order listings (a second listed order's card puts its "2249 : 1" ratios inside the box's area), the ratio field and scenery cost nothing. A window with no hover box is read in about 40 ms on the owner's frames in Firefox on the Mac, where reading everything with a colon in the box's area, and the line reader after, took 120 to 360 ms. A run is a list: its "worse than" row after exactly 5 prices, or 1 to 5 prices without one. (Tests that give rows without places make runs by their spacing, a gap of a whole number of spacings being rows unread, and try a run failing the checks without its top row.) Two runs are Available then Competing. One run is told by its arrow (< Available, > Competing), else by its place: at Competing's it's Competing; at Available's without banners it's Available; at Available's, the game's message "There are no available trades for these two items" (white letters just under the title, beside it: over a third of those pixels white with it, a few at most without) says it's Competing moved up, and without the message it's Available. The header banner over it ("AVAILABLE TRADES" / "COMPETING TRADES", its first word compared with the reference's, slid a little up and down) must not clearly say otherwise, where it can be read (button spacing 420 pixels or more; 0.15 apart). Every list must start where its first row belongs (within 0.6 of a spacing), or it's lost its best rows. Rows found with no list made of them (a row under the mouse cursor, say) are the answer: nothing is read, and the frame isn't read again another way. Reading the boxes round such rows line by line was tried: it took 2.2 to 3.5 s on a 2416 x 1431 frame with the cursor over a first row's stock, read nothing there, and no test screenshot needs it. **One list alone** (`empty`, for Import Market Ratios, §4.3): the other side has no trades when the list is Competing in Available's place under the game's message, or Available with no banners at its own higher place (0.164); anywhere else (Available under its banner in its usual place, as on a hover without Alt) the other side may only be hidden.
- **Speed.** 0.1 to 0.3 s per screenshot up to 1280 x 960, about 0.5 s at the two largest; the window and the lists take a few milliseconds, the rest is fitting rows. From 13-pixel text up, two sub-pixel offsets are tried instead of three. Shrinking large text instead read "111" as "11" and was dropped.
- **The line reader** (`readLines`, `js/snip.js`: text with no window to place its rows, as in the snip tests, is read line by line, and the font is learned with it) is made for the game's one fixed font rather than general OCR. Text is the brightest part of the box. Straight lit runs far longer than any stroke of a digit (over 60 pixels, or 12% of the box's shorter side) are the box's frame and row lines, and are dropped, as are pixel rows lit across most of the width. Characters are connected pixels. Lines are grouped from the characters themselves, not cut across the whole width: a character joins a line when each one's middle falls within the other, and a small one (a comma, a dot, under 0.6 of a line's height) joins the line it sits on. So scenery beside a loosely boxed list (a pinned window moved over the game) can't join its rows. Lines are split into words where there's a clear gap. Each word has its own digit height, as the game draws a long ratio smaller than the stock beside it ("2500.10 : 1   250,010"); a word of marks only (a colon) uses its line's, and the "worse than" arrow the ratio's after it. Each character is scaled to its word's digit height and compared with stored examples of the font (`data/glyphs.json`, loaded the first time) on a 16 x 16 grid, centred on its brightness, allowing a one-cell shift, and less a penalty for a different width (a 1 is far narrower than a 4). An example whose width alone puts it under 0.52 (below) can't win or come close, so it isn't compared: a game window's scenery, rarely digit-shaped, then costs little, and a whole window reads in half the time. A match under 0.55 is unreadable, and so is one that beats the next-best character by under 0.03 (in small text a 2 and an 8 come close): too close to call is never a guess. ". , :" are told by size and position, and a separator before exactly 3 digits is a comma (2,544), before 2 a decimal point (2.90). Text is what's over halfway from the box's usual brightness to its brightest; when that leaves a list unread, the box is read again with the line at 60%: small text (digits about 11 pixels in a game window shown on a big desktop) draws characters close enough to touch at halfway (a decimal point joined to the next digit, "484" as one shape), and the higher line parts them. Each list is taken from whichever reading has it. One that ends a number is dropped (the half-seen lower dot of a colon), and so is one on its own (a speck of the box's frame).
- **Small text** (digits about 9 pixels tall) draws some characters touching, e.g. a decimal point tucked under the next digit. A glyph that doesn't match is tried as two or three pieces, each a glyph that matches at 0.6 or more or a dot (never two separators in one shape: they're 2 or 3 digits apart, and a 2's tail cut off as a "dot" read ".25" as ".2.5"); the split whose weakest piece matches best wins. A separator cut off a shape with only one digit after it is a digit's tail and is dropped ("47,922" read as "47.92_2"). Only shapes that could be two or three characters are tried (a digit's height, at most 3.2 digits wide), cut only at the edges of their thin stretches (at most 40% of the fullest column lit), and not at all with more than 8 such edges: a loose snip's scenery would otherwise take minutes. Either side of a bridge one pixel thin is also a cut: in a resized window a 7's top bar can touch the next 1's flag ("21,171"), and all of a 7 is thin, so its edges miss the join. The colon's dots can be too dim to see at all, so a row read as three bare numbers ("1.33 1 4") is taken as "1.33 : 1" and stock 4.
- **Learning the font** (`tests/lines.json`, only for building the row reader's masters and reading the test snips; not shipped): each test snip's known lists teach the shape of each character, learned at whichever of the two brightness lines fits more rows. A line fits a row when, split at its widest gap, its ratio and stock have that row's numbers of characters ("1:3.50 6" is 4 and 1), and a list's rows are found as one evenly spaced run of fitting lines, placed by whichever rows fit (the first may not: "21,171" with touching characters). Placing it by the first row only once started a list at its second row, which has the same layout, and taught every row the labels of the one above. A header that only looks like some row ("Ratio  Stock" read as 2 and 3 shapes, like "1:4 168") is off that run, so it can't take a row's labels and shift the rows after it (which once taught a 5 as a 6). Rows with a character far (over 30%) from that character's usual width are dropped, as touching characters or a row whose count matched only by chance would teach the wrong shapes.
- **What counts as a list.** Rows read as "want : have" and stock, e.g. `1 : 2.90 19`, `1.33 : 1 4` or `2501 : 1 897,859` (either side may be 1; ratios over 999 have no comma, stock always does). A list ends at its "worse than" row: `<` ends Available Trades, `>` Competing. The game lists the best **5 prices** and then that row, evenly spaced; a thin market's list has fewer prices and no "worse than" row (a market with exactly 5 prices has none either), and each list starts where the window puts it (above). It must also check out: prices move one way down it (neighbours may show the same price, as the game rounds to two decimals: 7.50 then 7.50), neighbouring prices are within 30x of each other (thin books jump: 1 : 1 then 6 : 1, or a Mirror's 1 : 65000 then 1 : 5001), and the last row repeats the price above. A bigger jump ends the list there: it's an absurd order (10000 : 1 after 69 : 1, 145x) or a misread (a dropped decimal point jumps 100x, as the game always shows two), so the rows above it are the list when there are at least two, and the rows from it on, the "worse than" row among them, are left out (the order book stops there); with one row above it, that row is kept only when the other list was read too and its best price is within 10x of the row's (the two lists' best prices are within 5x over the test frames, Transmutation's 103 and 500; a dropped decimal point is 100x): Wild Crystallised Lifeforce / Chaos Orb's Competing 68 : 1 then 10000 : 1, beside Available's 41 : 1, is read as 68 : 1. Otherwise the list isn't read. The game centres each list's stocks, so a row whose stock is off its list's centre by more than 0.2 of a digit has lost or gained a digit, and its list isn't read (with 3 rows or more to tell the centre): a cursor over the "1" of "16,837" left "6,837", 0.245 off, where stocks read right are within 0.13 over the test frames. Anything else isn't read. A frame that reads wrong is meant to fail, never to fill in a wrong price.
- **Which boxes.** The game shows "want : have", its I Want the pair's first currency (the names say which, below). Its Available Trades fill the pair's Available Trades box (row have>want) and its Competing Trades the Competing one (row want>have); seen from the other side, they swap: the game's Available Trades are the other way round's Competing Trades. Only the lists read are filled.

## 5. Where prices come from

- **From the game, for 4 hours.** A price is in the calculation once it's been read from the game (§4.7) and stays until it's read again or for 4 hours, then it's forgotten (§4.3). In Competitive and Instant Trading a pair without one has no price, and routes that need it show "not scanned"; in Estimated Trading and on My Listings it's at its estimate, the latest hour's average (§3.2c). Nothing else is typed but Manual steps (§3.2b).
- `rates.json`'s averages also serve where no price is needed: volumes (an item page's volume, Traded last hour, Trade Volumes), stock and directions with no orders (§2.1a), fill times (§3.6), and the reader's check that a reading is within 3x of one of the pair's averages (§4.7).

## 6. Data pipeline

### 6.1 Source

GGG's public hourly currency-exchange digest:

```
GET https://web.poecdn.com/api/currency-exchange/<unix-hour>
```

- No authentication is needed.
- It covers every league in the PC realm.
- About 5 minutes after the hour closes, the data for that hour is final.
- `/<id>` returns the hour that starts at `id`, with `next_change_id = id + 3600`. The unfinished current hour comes back as **HTTP 404** whose body is still valid JSON: `{"next_change_id": id, "markets": []}`. That means "caught up".
- The response does **not** send CORS headers, so a browser can't read it. The authenticated `api.pathofexile.com` version needs a confidential client (`service:cxapi`), which can't run in a browser.

### 6.2 Hourly job

- Runs as an AWS Lambda on an EventBridge schedule at `HH:10` (`job/rates.py`), with a 300 s timeout.
- **Two games, one run.** It updates each game in turn (`GAMES` in `job/rates.py`):
  - **Path of Exile 1:** the PC realm (`/api/currency-exchange/<id>`), hubs Chaos and Divine, writing `html/rates.json` and `job/state.json` (keys in the bucket, §10).
  - **Path of Exile 2:** the `poe2` realm (`/api/currency-exchange/poe2/<id>`, same response format), hubs Divine, Exalted (`CurrencyAddModToRare`) and Chaos, writing `html/poe2/rates.json` and `job/poe2/state.json`. Its leagues use "HC …" for hardcore, which `league_kind` already handles.
  - A game that fails (e.g. a permission it doesn't have yet) is logged and skipped, so the other still updates; the run fails only if every game does. `{"games": ["poe2"]}` limits a run to one game.
  - The site deploy's `--delete` sync excludes both games' outputs.
- **State:** it keeps each game's working state in its state file in the bucket. That holds every pair plus its hour-by-hour volume history. Each run, it pages forward from the stored `nextChangeId`, merging each finished hour, until it's caught up. It fetches at most 30 hours per run. A first run, or `./deploy.sh job backfill`, starts `DAYS` days back. A missed run catches up on the next one.
- **What it tracks:** every pair of a currency against one of the game's hubs (and hub ↔ hub) that had trades on both sides, in every league except private and Ruthless ones (including "HC Ruthless …"). Pairs between two items are ignored.
- **Each pair** keeps its newest traded hour (`volA`/`volB`, `hour`) and the last `DAYS` days of hourly volumes. Pairs with no trades in that window, and history hours older than it, are dropped.
- **Outputs:**
  - `job/state.json` (with history, `Cache-Control: no-store`)
  - `html/rates.json` (served as `/rates.json`), the same data without the history plus the `recentA`/`recentB` and `dayA`/`dayB` totals and each league's `noOrders` (`max-age=300`), which the site loads. About 370 KB, or ~55 KB gzipped, at ~850 Allflame currencies.
  - `history/<game>/<day>/<HH>.json.gz`, every hour's markets, kept for good (§6.2a).
- Sends `User-Agent: rainofchaos/1.0 (+https://rainofchaos.app)`. The site URL is the contact, so no email address is needed.
- If the state file is missing (S3 returns AccessDenied or NoSuchKey, because the role has no `ListBucket`), the job starts empty.

`rates.json` format:

```json
{
  "generatedAt": 1791062984,
  "nextChangeId": 1791061200,
  "noOrdersHour": 1791057600,
  "leagues": {
    "Allflame": {
      "kind": "challenge-softcore",
      "chaosVolume": 3084950,
      "pairs": {
        "CurrencyModValues|CurrencyRerollRare": {
          "a": "CurrencyRerollRare", "b": "CurrencyModValues",
          "volA": 1160810, "volB": 3051,
          "recentA": 4600000, "recentB": 12100,
          "dayA": 27900000, "dayB": 74300,
          "hour": 1791050400,
          "stock": [5000000, 900]
        }
      },
      "noOrders": ["CurrencyModValues>CurrencyRerollRare"]
    }
  }
}
```

`volA`/`volB` and `hour` are the newest traded hour. `recentA`/`recentB` are the totals over the last 4 finished hours (§3.6), `dayA`/`dayB` over the last `DAYS` days. A league's `noOrders` lists the rows with no open orders in the latest digest (`noOrdersHour`, §2.1a). For a pair listed in the latest hour, `stock` is each currency's lowest stock on offer then (§2.1a). In `job/state.json`, each pair also has `history`: `[hour, volA, volB]` for every hour it traded in that window.

Item ids are the last path segment of the API's metadata id. A pair's key is the two ids sorted and joined with `|`. `a`/`b` and the volumes keep the order the pair was first seen in.

### 6.2a Market history

For finding trends by hour of the day and day of the week, every finished hour the job merges is also kept, for every pair, in a file of its own per game:

- **Key:** `history/<game>/<YYYY-MM-DD>/<HH>.json.gz` (`poe1` or `poe2`, the hour's UTC day and its two-digit UTC hour), under the prefix `HISTORY_PREFIX` (default `history/`). Gzip-compressed JSON, stored with `Content-Type: application/gzip` and `Cache-Control: no-store` (an archive, not served: CloudFront serves only `html/`).
- **What's in it:** every market of the digest, in every league except private and Ruthless ones, including item-to-item pairs and pairs that traded on one side or neither (the rates leave those out).
- **Each run** writes each hour it merged as its own file, without reading anything first. An hour read again (a backfill, or a run retried) overwrites its file. One file per hour means no read-modify-write of a growing file, and each run holds only its own hours in memory.
- It's written after the game's state and `rates.json`. A history write that fails is logged (`{"game", "history": <key>, "error"}`) and reported in the run's `failed` list as `<game>/history`; the rates and state are already written, and that hour is missing from the history.
- **Never pruned.** At ~1250 markets an hour (PoE1) and ~2400 (PoE2), measured on a real hour in October 2026, an hour's file is about 27 KB (PoE1) and 47 KB (PoE2), so a year is about 8,760 files and 240 MB for PoE1, and 410 MB for PoE2.

```json
{
  "game": "poe1",
  "hour": 1791050400,
  "fields": ["market_pair", "volume_traded", "lowest_stock", "highest_stock", "lowest_ratio", "highest_ratio"],
  "leagues": {
    "Allflame": [
      [["CurrencyRerollRare", "CurrencyModValues"], [1160810, 3051], [5000000, 900], [5600000, 960], [380, 1], [400, 1]]
    ]
  }
}
```

`hour` is the hour's start (unix seconds, as `nextChangeId`). Each market is a list of `fields`, the digest's own fields: `market_pair` as short ids, then each figure as `[a, b]` in `market_pair`'s order (0 where the digest gives none). `volume_traded` is how much of each currency traded that hour, `lowest_stock`/`highest_stock` how much was on offer at least and at most, and `lowest_ratio`/`highest_ratio` the digest's ratio range, each as two whole numbers.

### 6.3 Leagues

The league list comes from `rates.json`. Leagues are classified by name:
- `Standard`
- `Hardcore…` or `HC …` (hardcore)
- anything containing `Ruthless` (not tracked)
- names containing `(PL` (private)
- anything else, which counts as a challenge-softcore league

The default is the challenge-softcore league with the highest `chaosVolume` (total chaos traded in the latest hour). The user's choice is remembered. The dropdown lists only Standard, Hardcore, that challenge league, and `Hardcore <challenge league>`, in that order, by name only. Leagues missing from `rates.json` are skipped. Ruthless and private leagues stay in the file but aren't offered.

## 7. Client storage

All user state but the read history (below) is kept in `localStorage`, **per league**:
- ratios: only those read from the game: value, the decimals shown on each side (`digits`), the stock on offer at it (`stock`, in what that row's orders offer; the queue of §3.6) and when it was read (`verifiedAt`, ms; used for 4 hours, then dropped, §4.3).
- the rows' orders read from the game (`lists`, §3.2a), by row key: the levels as last read from either list, the "worse than" row's stock (`rest`, or null) and when they were read; dropped after 4 hours, as scans are, unless a started listing step trades on that row (its fill time counts what's ahead of it from them, §4.6)
- every read of those in the last hour (`reads`, by row key: when, and the levels), for undercutting (§3.6); older ones are dropped

What's dropped is dropped from every league, each time a page is drawn, and the state is saved once per read imported, so it stays small.
- Chaos or Div mode (`base`, a hub's currency id) and the starting amount for each hub (`start`, by id). A `base` that isn't one of the game's starting currencies falls back to its first.
- selected league
- listings (`listings`, §4.6), each with its league, in one list: whether it's completed (and when), the item, start currency and amount, when it was added, and per step its Type choice (for Manual, with its price), its state (waiting, in progress or done) and, once started, its Have, the step as it was then (`fixed`: ratio with its digits, amounts, gold), when it was started, its fill time then, what that was worked out from (the pace, the undercutting, the stock ahead and the stock at its price) and, once done, when (`doneAt`). Also the listing's expected profit at add (`expected`), for a cancelled step its whole order (`whole`, `fixed` then being what traded), and for a step inserted after one (`repost`) what it trades (`left`, of the same Have) and its own Type choice (`method`). That's for comparing fill times with the real ones (`?debug`'s reads file, §4.7)

The **read history** (`js/history.js`) is apart, in IndexedDB, since it would outgrow `localStorage` (one key, rewritten at every save): a database per game (`<storage key>:reads`, e.g. `rainofchaos:v1:reads`), store `reads`, one record per list read, added as it's read and never rewritten: `{ league, key, at, levels, rest }` (the row key, when, and the levels and "worse than" stock as `lists` has them), with indexes on `at` and on `[league, at]`. Once per page load, records older than 2 weeks (`HISTORY_FOR`) are deleted; a scan running out (§4.3) leaves them. It's kept only for analysis (§3.6, and prices by hour of the day and day of the week); the writes aren't waited for, and when IndexedDB is blocked or fails the page works without it.

The site has to work even when storage is unavailable, so it falls back to in-memory state. Nothing is exported or imported: scanned prices and what's learned from them stay in the browser.

## 9. Tech stack

- **Site:** plain HTML, CSS and JavaScript ES modules in `html/`, with no build step and no dependencies. `html/js/calc.js` holds the calculation. `tests/calc.test.js` checks it against the §8 fixtures, either in a browser (`tests/index.html`) or headless with macOS's built-in JavaScriptCore (`jsc -m`), so Node isn't needed.
- **Hourly job:** Python on AWS Lambda, using only the standard library (`urllib`, `json`) plus the `boto3` that the Lambda runtime provides.
- **Cost:** about $0/month. Each run fetches only the newest hour (≈1.2 MB, ≈0.4 s) and merges it into the job's state, which `rates.json` is written from. That works out to 720 runs/month at ≈360 GB-s, well inside Lambda's always-free allowance. EventBridge, S3, CloudFront and logs are all free or fractions of a cent at this volume.

## 10. Infrastructure (Terraform)

The infrastructure is Terraform in a separate private repo and follows its conventions:
- `provider.tf`: `us-east-1`, an S3 backend for its state, and the shared base stack's remote state.
- One file per concern, plus a `locals.tf`.

Resources:

| File | Resources |
|---|---|
| `s3.tf` | private site bucket (all public access blocked), bucket policy letting only CloudFront OAC read, and only `html/*` |
| `cloudfront.tf` | distribution with OAC, origin path `/html` (so `/rates.json` is the object `html/rates.json`), `index.html` as the default object, managed `CachingOptimized` policy (honours each object's `Cache-Control`). Routing uses hashes (`#/item/<id>`), so there are no error-page rewrites, which would also hide a missing `rates.json` behind HTML. |
| `route53.tf` | `rainofchaos.app` A/AAAA alias at the apex → CloudFront (uses the `rainofchaos.app.` zone, created by hand) |
| `lambda.tf` | Python 3.13 function `rainofchaos-rates` (256 MB, 300 s timeout for PoE2's first catch-up, handler `rates.handler`), log group with 14-day retention, env vars `BUCKET`, `RATES_KEY` (`html/rates.json`), `STATE_KEY` (`job/state.json`), `POE2_RATES_KEY`, `POE2_STATE_KEY`, `HISTORY_PREFIX` (`history/`), `SITE_URL` |
| `scheduler.tf` | EventBridge Scheduler at `cron(10 * * * ? *)` → Lambda |
| `iam.tf` | Lambda role: `s3:GetObject`/`s3:PutObject` on both games' rates and state files and under `history/` only, CloudWatch logs; Scheduler role: `lambda:InvokeFunction`; the site deploy role may write and delete only under `html/`, and never those four files |

**How code gets deployed:** this follows the ECS pattern, where Terraform owns the infrastructure and the app repo ships the code.
- Terraform creates the Lambda with a placeholder zip and sets `ignore_changes = [filename, source_code_hash]`. The rainofchaos repo deploys the job with `aws lambda update-function-code`.
- **The bucket** (`rainofchaos.app`) holds three folders. `html/` is everything the site serves: CloudFront's origin path is `/html`, so the viewer's `/js/app.js` is the object `html/js/app.js`, and its bucket policy reads nothing outside `html/`. It's the repo's `html/` folder plus what's written there by others: the job's `html/rates.json` and `html/poe2/rates.json`, the deploy's `html/version.json`, `html/poe1` and `html/poe2`, and `html/debug-algorithm/` (pages uploaded by hand). `job/` is the job's private state (`job/state.json`, `job/poe2/state.json`), and `history/` its market history (§6.2a); neither is served.
- The site is deployed with `aws s3 sync html/ s3://rainofchaos.app/html/ --delete` (excluding `rates.json`, `poe2/rates.json`, `version.json`, `poe1`, `poe2` and `debug-algorithm/*`). There are no hashed filenames, so every file is `no-cache` and revalidates by ETag, and `/*` is invalidated afterwards. The tests (`tests/`, at the top of the repo) aren't deployed.
- The game pages: `deploy.sh site` also uploads `html/index.html` as the objects `html/poe1` and `html/poe2` (no extension, `Content-Type: text/html`), so `/poe1` and `/poe2` serve the page with no CloudFront changes. The sync's `--delete` excludes them. Asset paths in the page are absolute (`/css/…`, `/js/…`). Locally, `python3 tools/serve.py` does the same mapping: it serves `html/` at `/`, plus `/tests/` and `/html/` as those folders of the repo, so the tests' imports (`../html/js/…`) resolve.
- `deploy.sh` handles both deploys. Run by hand, it needs the AWS profile to use (`AWS_PROFILE=<profile> ./deploy.sh …`), and stops if none is set. **On merge to `main`, `.github/workflows/deploy.yml` runs it automatically**: `job/` changes deploy the Lambda (`./deploy.sh job`), and `html/` or `deploy.sh` changes deploy the site (`./deploy.sh site`, with the calc tests run under Node 22). Running the workflow by hand deploys both. Deploys run one at a time, in merge order (a `deploy` concurrency group that never cancels a running deploy). GitHub keeps only one waiting run per group, cancelling an older waiting one when a newer arrives, so what changed is measured from the last deploy that succeeded (the `deployed` tag, moved to each successful run's commit), not from the push before: a run cancelled while waiting has its changes deployed by the next. It authenticates via OIDC as its own role, `rainofchaos-deploy` (from Terraform, its ARN in the repo secret `AWS_DEPLOY_ROLE`, a secret so the logs never show the account id), which only this repo's `main` branch can assume and which can't write or delete the job's four files (`html/rates.json`, `html/poe2/rates.json` and the state files). It records GitHub deployments with `gh api` (the repo is public, so it uses only public actions). The stack outputs `bucket`, `distribution-id`, `function-name` and `url`.
- **Releases:** each site deploy from `main` is a release, versioned `YYYY-MM-DD-N` (its UTC date, and which release of that day it is, counting from 1): the workflow works the number out from the existing tags, `deploy.sh site` uploads `html/version.json` (`{ version, commit }`; not a file in the repo's `html/`, and kept out of the sync's `--delete`) with the site, and once it's deployed the workflow tags the commit and publishes the GitHub release (`gh release create`, notes from the merged PRs). A deploy by hand uploads `local-<commit>`; job-only deploys aren't releases. The page doesn't show the version; `?debug`'s log names it (§4.7), and the local server (`tools/serve.py`) answers `version.json` with `local-<commit>` too.

`shutdown.sh` / `startup.sh` apply every `application/*` stack. This stack declares no `desired_capacity` or `nat` variable and costs nothing when idle, so those scripts leave it running.
